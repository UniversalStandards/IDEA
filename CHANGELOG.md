### Fixed — 2026-10-01 session (PR #173 review response)
- `src/adapters/upcloud-worker-factory/index.ts` — `BrokerSessionResponseSchema.endpoint` validated only `z.string().url()`, which accepts any scheme (`https://`, `file://`, …) for what is always meant to be a `wss://` CDP endpoint; a compromised or misbehaving broker response would have passed validation and been handed back as something to connect to. Added a refinement requiring the `wss://` scheme. (Codex/Copilot finding.)
- `src/adapters/upcloud-worker-factory/index.ts` — `createSession()` had no rollback path: if Vault leasing failed *after* the broker already allocated a worker for the session, that worker was never torn down (nothing had added the session to `this.sessions` yet, so neither `endSession()` nor `shutdown()` could ever find it), and any credential scopes already issued for earlier paths in a multi-secret request were left live with nothing able to reach or revoke them. `leaseVaultSecrets()` now rolls back its own partially-issued scopes on a mid-loop failure, and `createSession()` now tears down the broker session on any post-allocation failure before rethrowing. (Codex P1 finding.)
- `src/api/admin-api.ts` — `requireAuth` verified only the JWT signature, not its `scope` — since every bearer token this hub issues is signed with the same `JWT_SECRET`, a worker-session token (minted by the adapter above) could be replayed against the Admin API and would pass as authenticated, reaching capability deletion, approvals, and audit data. `requireAuth` now explicitly rejects any token carrying `scope: 'worker-session'` with 403. (Codex P1 finding — security.)
- `src/api/admin-api.ts` — `GET /admin/capabilities`'s existence check accessed a `Record<string, unknown>` index-signature property with dot notation (`...).getCapabilities`), which is a compile error on this project's strict config; switched to bracket notation. - `tests/upcloud-worker-factory.test.ts` — fixtures built `expiresAt` from live `Date.now()` calls with no fixed clock, and the adapter's own internal `Date.now()` reads (duration metrics, Vault-token cache expiry) were equally non-deterministic; `AGENTS.md` §8 requires tests to be deterministic ("no `Date.now()` ... without mocking"). ### Fixed — 2026-10-01 session (PR #173 third review round)
- **`src/adapters/upcloud-worker-factory/index.ts` — worker-session tokens now sign with a key *derived* from `JWT_SECRET`, not `JWT_SECRET` itself** (`deriveWorkerSessionKey()`, HMAC-SHA256 over a fixed versioned context string). Previously, isolating a worker-session token from admin/runtime access depended entirely on every verifier that checks `jwt.verify(token, cfg.JWT_SECRET)` remembering to also reject `scope === 'worker-session'` by hand. Auditing every such verifier while fixing this turned up exactly the failure mode the review warned about: **`src/multitenancy/TenantMiddleware.ts`** had no such check at all — a worker-session token would have verified there and (had it ever carried an `orgId`/`org_id` claim, which nothing currently prevents) granted tenant context. With a derived key, every current and future verifier that checks straight against `JWT_SECRET` rejects a worker-session token on signature mismatch alone; the existing explicit scope checks in `admin-api.ts`'s `requireAuth` and `transport/middleware/auth.ts`'s `isTransportAuthorized()` are now defense-in-depth rather than the only defense, and their comments were updated to say so. `TenantMiddleware.ts` gained an explanatory comment plus its first test file, `tests/tenant-middleware.test.ts` (3 cases). `tests/upcloud-worker-factory.test.ts` gained 4 cases covering the derivation itself and both the "signed with the wrong key" and "signed with `JWT_SECRET` directly" rejection paths; `tests/admin-api.test.ts` gained one covering the real (derived-key-signed) rejection path specifically, distinct from the existing simulated-worst-case test. (Copilot High-severity finding: "Shared JWT secret enables compromised workers to mint privileged tokens.")

### Fixed — 2026-10-01 session (PR #173 fourth review round)
- **`src/adapters/upcloud-worker-factory/index.ts` — `leaseVaultSecrets()` inserted the caller-supplied `vaultSecretPaths` into the request URL with no validation or encoding.** A path such as `../../sys/leases/lookup` normalizes outside `VAULT_SECRET_MOUNT`, letting whoever can request a worker session make the adapter's own Vault AppRole token reach any Vault API path that token's policy allows, not just secrets under the configured mount. Added `encodeVaultSecretPath()`: rejects empty/`.`/`..` segments and percent-encodes every remaining segment individually (so a segment can't smuggle a pre-encoded traversal sequence past the check), run over every requested path *before* any Vault call is made — a malformed path in a multi-secret request is now rejected up front rather than partway through. (Copilot High-severity finding.)
- **`src/adapters/upcloud-worker-factory/index.ts` — `endSession()` and the rollback path in `leaseVaultSecrets()` only revoked the hub's own encrypted copy of a leased secret via `credentialBroker`, never the underlying Vault lease itself.** A worker (or anything downstream that already received the credential) could keep using it until Vault's lease TTL expired on its own — potentially well after the session that leased it had ended. `CredentialScopeRef` gained an optional `vaultLeaseId`, populated from Vault's own lease response; a new `revokeVaultLease()` calls Vault's `PUT /v1/sys/leases/revoke` for it, from both normal teardown (`endSession()`) and the mid-request rollback path. Best-effort by design — a Vault-side failure is logged loudly rather than blocking the rest of teardown, since the lease's own TTL remains a backstop. (Copilot High-severity finding.)
- `docs/gates/upcloud-worker-factory.md` — Gate 1's frozen decision text still described worker-session tokens as signed with `JWT_SECRET` directly, contradicting the third-review-round fix above; an external verifier built from this doc would use the wrong key and reject every real session token. Corrected in place (with an "Updated 2026-10-01" note, not versioned to v2 — no UpCloud-side build exists against the old text yet). (Copilot Low-severity finding.)
- `tests/transport-auth.test.ts` — file header comment still described worker-session tokens as signed with the hub's plain `JWT_SECRET`; corrected to describe the derived-key rejection as the actual (and primary) defense, with the explicit `scope` check as the defense-in-depth layer the tests in this file actually exercise. (Copilot Low-severity finding.)
- Added test coverage for both High-severity fixes: a rejected-traversal-path case (asserting zero Vault calls are made, not even AppRole login), a percent-encoding case, Vault-revoke assertions added to both the existing successful-teardown and partial-multi-secret-rollback tests, and a case confirming a Vault-side revoke failure is logged but does not block the rest of teardown.

### Fixed — 2026-10-01 session (PR #173 fifth review round)
- **`docs/gates/upcloud-worker-factory.md` — Gate 1's text instructed a future external (UpCloud-side) verifier to "compute `deriveWorkerSessionKey(JWT_SECRET)` itself," which means handing that verifier `JWT_SECRET` so it can derive the key locally.** That defeats the entire point of key derivation: a verifier outside this hub holding the hub-wide root secret is one compromise away from an attacker minting admin-api and runtime tokens too, not just worker-session ones — the exact blast-radius expansion key separation exists to prevent. No code in this repo ever transmits `JWT_SECRET` externally (confirmed by inspection — this was a documentation-contract defect, not a code defect), but the doc would have told whoever builds the real external verifier to do the wrong thing. Corrected in place (second same-day correction, same rationale as the first: no UpCloud-side build exists against the old text yet): an external verifier must never be given `JWT_SECRET`; instead the hub computes `deriveWorkerSessionKey(JWT_SECRET)` once and provisions only that resulting derived value to the external side as its own independent secret, out-of-band. Noted asymmetric signing (RS256/EdDSA, distributing only a public key) as the stronger design any real external verifier should adopt. (Copilot High-severity finding.)
- **`src/adapters/upcloud-worker-factory/index.ts` — `endSession()` swallowed a failed broker-side session-teardown call and deleted the session from local state regardless.** Credentials were (correctly) still revoked unconditionally, but the remote worker and its still-valid session token could remain live and reachable, with no record left to retry tearing it down — a later reconciliation pass had nothing to find. `WorkerSessionState` gained an optional `teardownPending` flag; on a broker-teardown failure the session is now retained (credential scopes cleared, since those are already revoked) instead of discarded, and a new `listPendingTeardownSessions()` surfaces it for an ops/reconciliation pass. Calling `endSession()` again for the same `sessionId` retries only the broker-side `DELETE` (idempotent — there is nothing left to revoke). (Copilot High-severity finding.)
- Added test coverage for both fixes: a case asserting a failed broker-teardown call still revokes credentials/Vault leases unconditionally while retaining the session with `teardownPending: true` and an empty `leasedCredentialScopes`, and a retry case confirming a second `endSession()` call completes teardown once the broker call succeeds.

### Fixed — 2026-10-01 session (PR #173 sixth review round)
- **`src/adapters/upcloud-worker-factory/index.ts` — `verifySessionToken()` cast the JWT's `capabilities` claim straight through without validating its contents** (a non-array silently became `[]`; an array containing anything other than `'browser'`/`'desktop'`, e.g. `['admin']`, was returned unchanged). A valid signature only proves the token was minted by something holding `deriveWorkerSessionKey(JWT_SECRET)` — it says nothing about whether the claims inside still conform to this function's declared type, so a malformed-but-validly-signed token could violate the `WorkerSessionCapability[]` contract downstream code relies on and potentially slip past a capability check that isn't doing an exact-match comparison. Added a `WorkerSessionCapabilitySchema` (`z.enum(['browser', 'desktop'])`) and validate the whole claim with `z.array(...).min(1).safeParse()`, throwing on anything that doesn't conform. (Copilot High-severity finding.)
- **`src/adapters/upcloud-worker-factory/index.ts` — `shutdown()` used `Promise.allSettled()`'s rejection count as its only signal of what failed, but `endSession()` resolves normally even when the broker-side teardown call fails** (it marks the session `teardownPending` rather than throwing — see the fifth-round fix above). `shutdown()` therefore always logged every session as cleanly ended, even when some were only teardown-pending, silently losing the in-memory record the moment the process exits with no automatic retry path across a restart. `shutdown()` now checks `listPendingTeardownSessions()` after every `endSession()` call settles and logs a loud, explicit error naming the affected session IDs instead of claiming full success. (Copilot Medium-severity finding.)
- **`src/core/runtime-manager.ts` — `getStatus()`'s `upcloud-worker-factory` subsystem entry always reported `healthy: true`**, even when one or more sessions were sitting in `teardownPending` (an operational fault: a leaked remote worker whose credentials are revoked but whose broker-side teardown never completed). Readiness/health monitoring had no way to see this. The entry now reports `healthy: pendingTeardowns === 0` and includes the pending count in its detail string when nonzero. Not independently unit-tested this round — `src/core/runtime-manager.ts` has no existing dedicated test file (a pre-existing gap predating this session; `tests/admin-api.test.ts` fully `jest.mock()`s the module rather than exercising the real implementation), and standing up a new test harness for the whole `RuntimeManager` class (mocking 8+ subsystems) to cover one health-check branch was judged disproportionate scope for this fix; verified by code inspection, `tsc`-equivalent `eslint` type-aware linting of the file (clean aside from one pre-existing, unrelated `consistent-type-imports` violation on an untouched import line), and by `tests/upcloud-worker-factory.test.ts`'s existing coverage of the underlying `listPendingTeardownSessions()` data source it reads from. Worth a real `tests/runtime-manager.test.ts` in a future session regardless of this specific fix.
- **`docs/gates/upcloud-worker-factory.md` — the fifth round's own correction text was itself self-contradicting**: it said `api/admin-api.ts`, `transport/middleware/auth.ts`, and `multitenancy/TenantMiddleware.ts` all "compute `deriveWorkerSessionKey(JWT_SECRET)` itself," same as `verifySessionToken()` — but if those three verifiers actually did that, they would *accept* a genuine worker-session token (a correct signature match), not reject it. Corrected in place (third same-day correction): only `verifySessionToken()` computes the derived key; the other three are unchanged and still verify with `JWT_SECRET` directly, which is precisely why a worker-session token fails there (key mismatch, not recognition). (Copilot Low/Medium-severity finding.)
